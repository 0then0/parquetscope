# Prefetch lab

One question: for one fixed set of Parquet files, how do DuckDB 1.5.6 and 2.0.0 differ in the HTTP reads they issue when `disable_parquet_prefetching` is off and on? The shape follows [duckdb/duckdb#25704](https://github.com/duckdb/duckdb/issues/25704): one old file that holds a single large row group, and several small files with newer rows, read through a filtered TOP-N query.

This is a measurement of loopback HTTP requests on one machine. It is not a claim about S3, about other data, or about speed. The issue's figures (33 GET without the setting, 1,697 with it, on DuckDB 2.0.0 against 26 files on S3) belong to its dataset and environment. They are not expected here and were not reproduced as such. Upstream state when this lab was recorded (2026-11-07): the issue is open; the reporter measured the same amplification on the 2.0.0 release; the candidate fix [duckdb/duckdb#25961](https://github.com/duckdb/duckdb/pull/25961) is open and marked stale, so it is not part of either engine measured here.

## Data

Generated by [scripts/prefetch_lab.py](../../scripts/prefetch_lab.py) with seed 20261107, columns `id`, `ts`, `account_id`, `amount_cents` (`BIGINT`), `category` and `note` (`VARCHAR`), Zstandard, 32 KiB data pages:

- `part-00-old.parquet`: 400,000 rows in **one row group** (12,811,863 bytes), `ts` spread over the whole range. It is listed first in the manifest.
- `part-01-new.parquet` … `part-07-new.parquet`: 40,000 rows each in 4 row groups (about 1.28 MB each), `ts` only in the newer 40% of the range.

8 files, 680,000 rows, 21,780,677 bytes. [manifest.json](manifest.json) pins each file's size and SHA-256 (the report also lists them). Another PyArrow version can write different bytes for the same data; compare regenerated hashes with the committed ones first. The Parquet files are generated into `.runtime/prefetch-lab/` and ignored by Git, so this copy of the manifest documents the pins and is not directly usable. Use `.runtime/prefetch-lab/manifest.json` after a run.

## Query

```sql
SELECT id, ts, account_id, category, amount_cents, note FROM input
WHERE amount_cents >= 5000 AND category <> 'void'
ORDER BY ts DESC, id DESC LIMIT 200
```

The generator computed the expected 200 rows with pyarrow alone (read the files back, filter, sort), without DuckDB. All 12 captures matched its row count and ordered digest `08b7215b…739ca8`, and the first rows matched the preview. 74 of the 200 rows come from the old file, so its large row group is genuinely read.

## Configurations and conditions

Four configurations: DuckDB 1.5.6 and 2.0.0, each with `disable_parquet_prefetching` set explicitly to `false` ("on") and to `true` ("off"). The engine read back every value and the capture records it as `verified`.

Identical in all four: 4 threads, a 256 MiB engine memory limit, external file cache off, HTTP metadata cache off, keep-alive on, 3 retries, 30 s timeout, retry wait 100 ms, backoff 4. The worker pins the HTTP options after loading httpfs, and the captures' effective settings agree (4 and 4.0 for the backoff are the same value printed differently). The memory limit was chosen with `calibrate`: all four configurations completed the query at the minimum of 64 MiB ([calibration.json](calibration.json)), so 256 MiB leaves a margin without being a variable.

Each run is a fresh worker process in the isolated environment of its engine (DuckDB 1.5.6 with httpfs `4bc690d`, 2.0.0 with httpfs `77392a7207`). Three repetitions rotate the order by one position per round, so no configuration is always first or last. OS and disk caches are not controlled.

## Reproduce

```sh
uv sync --frozen
uv run parquetscope setup --engine 1.5.6
uv run parquetscope setup --engine 2.0.0
uv run python scripts/prefetch_lab.py run --output docs/prefetch-lab
```

`setup --engine` needs the network and installs each DuckDB wheel and its httpfs into `~/.cache/parquetscope/engines/` (or under `PARQUETSCOPE_HOME`), never into the project's `.venv`. DuckDB 2.0.0 needs Python 3.11 or newer to host its environment. The run itself uses only prepared environments. `uv run python scripts/prefetch_lab.py calibrate` repeats the memory calibration. To inspect one live capture through the regular path:

```sh
uv run parquetscope capture --manifest .runtime/prefetch-lab/manifest.json \
  --engine 2.0.0 --prefetch off --output off.parquetscope.json \
  --sql "SELECT id, ts, account_id, category, amount_cents, note FROM input WHERE amount_cents >= 5000 AND category <> 'void' ORDER BY ts DESC, id DESC LIMIT 200"
```

Compare all four offline: open any file in [viewers/](viewers/) (standalone HTML, repetition 1 of each configuration) in a browser and use **Import artifact** to add captures from [captures/](captures/), then **Compare runs**. Or use `uv run parquetscope serve --artifact docs/prefetch-lab/captures/<a>.parquetscope.json --artifact docs/prefetch-lab/captures/<b>.parquetscope.json`. [report.json](report.json) holds every run's metrics and [SHA256SUMS.txt](SHA256SUMS.txt) the checksums.

## Observations

Medians of 3 repetitions (min to max in the report). The request counts were identical or within a few requests across repetitions; durations vary and are not used for any conclusion. The server's own trace was used for the request and byte columns; its GET and HEAD counts equal the engine log's in every capture.

| Configuration | GET | HEAD | Server wrote | Unique coverage |
| --- | ---: | ---: | ---: | ---: |
| 1.5.6, prefetch on | 125 | 9 | 20.9 MiB | 20.8 MiB |
| 1.5.6, prefetch off | 576 | 9 | 542.8 MiB | 20.8 MiB |
| 2.0.0, prefetch on | 44 | 9 | 20.9 MiB | 20.8 MiB |
| 2.0.0, prefetch off | 2,969 | 9 | 21.0 MiB | 20.8 MiB |

- On 2.0.0 disabling prefetch multiplied the GET count by about 67 (44 to 2,969) while the bytes written stayed at about 21 MiB: many small reads of the same data. The direction matches the amplification reported in the issue. The local factor, the S3 factor (51) and the counts differ because the data, storage and latency differ.
- On 1.5.6 disabling prefetch multiplied the GET count by about 4.6 and the bytes written by about 26: 543 MiB were written for 20.8 MiB of unique data. The captures show repeated coverage of the file set instead of many tiny reads. This lab does not explain why, and it differs from the issue's S3 figures for 1.5.6 (79 to 133 GET).
- With prefetch on, 2.0.0 issued fewer GETs than 1.5.6 (44 vs 125) for the same bytes.
- Every configuration read essentially the whole file set (unique coverage 20.8 MiB of 20.8 MiB): the 200-row TOP-N did not let any file be skipped.

## Limits

- **Loopback, not S3.** There is no network latency, no object-store listing or retry behavior, and a local server answers every request immediately. The issue's slowdown from 2 s to 20 s is a latency effect that this lab does not model. Local SELECT durations (about 70 to 820 ms) are one machine's figures.
- **Server-written bytes are not DuckDB's bytes.** They count bytes the local listener wrote to the socket. They are not bytes DuckDB received, decoded or used. The same holds for the "confirmed ranges", which come from the engine's own log and agree here with the server's records.
- **Correlation differs by engine.** DuckDB 1.5.6 echoes the server's request ID header. DuckDB 2.0.0 redacts it in its log (`"redacted"`), so its log rows were paired with the server's records by request content: file, method, requested range, status, response interval and length, in start order. The pairing cannot change any count or total, and every group matched exactly in all captures, but it is a weaker identity than an echoed ID. Each artifact records which was used (`engine.request_correlation`).
- One dataset, one machine, one query, three repetitions. Counts may differ elsewhere.
- Hashing and footer reads for manifest preparation happen before each capture and are not part of the measurement.

Recorded with ParquetScope 0.2.0, PyArrow 26.0.0, macOS arm64, Python 3.13.18 (details in [report.json](report.json)).
