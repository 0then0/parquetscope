# Partition-pruning lab

One question: for the same Parquet bytes, which files does DuckDB 1.5.6 request when they sit in a flat directory and when they sit in Hive-style `month=N/` directories, and how does that change for a selective and a non-selective query?

This is a measurement of loopback HTTP requests for one workload on one machine. It is not a claim about S3, about other DuckDB versions, or about speed or cost. Behavior around [duckdb/duckdb#21347](https://github.com/duckdb/duckdb/issues/21347) is not reproduced: that issue is closed, concerns S3 globbing, and an explicit URL list does not list or glob.

## Data

Generated by [scripts/pruning_lab.py](../../scripts/pruning_lab.py) with seed 20261101: 6 months × 2 files × 20,000 rows = 240,000 rows, 12 files (2,590,457 bytes), 5,000-row row groups, Zstandard, columns `event_id`, `month`, `account_id`, `amount_cents` (all `BIGINT`) and `region`. Each file is written once and **copied byte for byte** into both layouts:

- `flat/`: `m01-data-0.parquet` … `m06-data-1.parquet`; manifest reads with `hive_partitioning: false`.
- `hive/`: `month=1/data-0.parquet` … `month=6/data-1.parquet`; manifest reads with `hive_partitioning: true`. Basenames repeat across directories.

Each file stores its `month` value (a constant) as an ordinary column, so the bytes are identical in both layouts and only the logical location and one read parameter differ. In the Hive layout the same value is also in the path. The lab verifies that the stored value equals the path value in every file. The manifests ([flat](flat/manifest.json), [hive](hive/manifest.json)) pin each file's size and SHA-256. The script rewrites the manifests with the pins of the bytes it just wrote. Another PyArrow version can write different bytes for the same data, so compare the regenerated manifests with the committed ones before comparing captures.

## Queries

```sql
-- selective: one partition value
SELECT count(*) AS n, sum(amount_cents) AS total_cents, sum(event_id % 97) AS checksum
FROM input WHERE month = 3
-- control: same column, every month matches
SELECT count(*) AS n, sum(amount_cents) AS total_cents, sum(event_id % 97) AS checksum
FROM input WHERE month >= 1
```

Aggregates are exact integers. Independent of DuckDB, the generator computed the expected results from the Python values: selective `40000, 1999029613, 1920427`; control `240000, 12014029617, 11519175`. Every capture matched, and the ordered result digests agree across layouts. The lab also checked, with pyarrow only, that the file bytes are identical in both layouts and that the data are equal row for row after sorting by `event_id`.

## Reproduce

```sh
uv sync --frozen
uv run parquetscope setup
uv run python scripts/pruning_lab.py --output docs/pruning-lab
uv run parquetscope serve --manifest docs/pruning-lab/flat/manifest.json \
  --manifest docs/pruning-lab/hive/manifest.json
```

The script regenerates the data, verifies it, captures 3 cold-client repetitions (a fresh worker each; OS and disk caches are not controlled) per layout and query, and writes `captures/`, `viewers/` (standalone HTML for repetition 1), `report.json` and `SHA256SUMS.txt`. Parquet files are generated and ignored by Git. Hashing and footer reads for manifest preparation happen before each capture and are not part of the HTTP measurement.

Recorded with ParquetScope 0.2.0, DuckDB 1.5.6, httpfs `4bc690d`, PyArrow 26.0.0, macOS arm64 (details in [report.json](report.json)). Open any standalone viewer in [viewers/](viewers/) directly in a browser. Each opens on **Files**.

## Observations

Medians of 3 repetitions. The spread of the request counts and byte totals was zero: all three repetitions of each combination gave identical GET, HEAD and server-written values. Only `query_duration_ms` varied (selective flat 17.5 to 22.4 ms, selective Hive 11.3 to 12.1 ms, control flat 34.4 to 35.8 ms, control Hive 25.1 to 26.1 ms). Those timings are one machine's loopback figures and are not used for any conclusion.

Selective query (`month = 3`):

- flat: 29 GET + 13 HEAD, 622,872 server-written bytes; all 12 files received a GET.
- Hive: 12 GET + 4 HEAD, 474,496 server-written bytes; 3 files received a GET and 9 files received no request.

The 3 Hive files with requests are `month=3/data-0.parquet`, `month=3/data-1.parquet` and `month=1/data-0.parquet`. The last is the first file in the manifest. Its requests start during view creation (binding) and again in the SELECT: a HEAD and a 16,384-byte GET each time. So a file outside the predicate was still requested, and files that were never requested are the 9 others. In the flat layout, of the 10 files that cannot match `month = 3`, the 9 that were not read for binding each received one HEAD and one 16,384-byte GET of their final bytes and nothing more; the first file received two of each. Binding accounts for 2 requests in every combination.

Control query (`month >= 1`):

- flat: 109 GET + 13 HEAD, 2,677,305 server-written bytes; 12 files with GET.
- Hive: 61 GET + 13 HEAD, 2,671,785 server-written bytes; 12 files with GET.

The control confirms the lab measures something: with a predicate that cannot exclude any month the Hive layout also requests all 12 files. The unique coverage is identical (2,518,229 bytes in both). The flat layout issued 48 additional GETs of 115 bytes; each interval intersects a `month` column chunk and there is one per row group per file (12 × 4). The Hive layout issued none. That the flat reads exist because the engine evaluated `month` from stored data while the Hive key came from the path is a plausible explanation that this lab does not test.

## What this does and does not show

- In this workload, with these settings, Hive pruning left 9 of 12 files with no recorded request, and the flat layout recorded requests for every file even though 10 of them could not match. Request totals depend on workload, file sizes, DuckDB version and settings; there was no run-to-run variation here, which does not guarantee any.
- "No recorded request" is complete-capture evidence for this trace (all 12 captures are complete and reconciled). It would not prove non-access in an incomplete trace.
- An interval overlapping a column chunk does not show that the column was decoded or used. The 16,384-byte tail read of a flat file covers the footer plus the end of a preceding chunk.
- Server-written bytes are not total application I/O. Preparation read every file in full outside the measurement.
- Nothing here measures object-store latency, request cost or listing behavior.
